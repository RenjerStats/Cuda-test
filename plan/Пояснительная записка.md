# Пояснительная записка

**Аннотация**

Работа направлена на создание C++ библиотеки, которая упрощает разработку и проверку CUDA-кода за счет двух ключевых механизмов: автоматизации изолированных Unit-тестов GPU-ядер и автоматизированного подбора конфигураций запуска с профилированием. Библиотека интегрируется с Google Test и Google Benchmark, формирует рекомендации по параметрам запуска (grid, block, shared memory) и предоставляет метрики для диагностики узких мест.

**Часть I. Концептуальная**

**1. Актуальность и постановка проблемы**

CUDA-код часто проверяется недостаточно изолированно: корректность логики и производительность тестируются в составе крупного приложения, что затрудняет воспроизводимость экспериментов и диагностику ошибок. В типичном проекте разработчик вручную подбирает параметры запуска ядра и вручную измеряет время, что:

- требует времени
- создает риск недооптимизированных конфигураций
- Приводит к созданию разных подходов к созданию конфигураций у разных программистов в рамках одного проекта

Отдельная сложность связана с тем, что время выполнения CUDA-задачи включает не только время ядра, но и затраты на выделение памяти, копирование данных на устройство и обратно, синхронизацию. Без этапного профилирования выводы о медленном коде ядра часто оказываются неверными.

**2. Объект, предмет, цель, гипотеза**

- Объект исследования: процесс разработки и тестирования CUDA-компонентов в C++ проектах.
- Предмет исследования: методы автоматизации изолированного тестирования и автоподбора параметров запуска CUDA-ядер.
- Цель: разработать библиотеку на C++, снижающую трудоемкость разработки надежного GPU-кода за счет автоматизации Unit-тестирования и поиска эффективных конфигураций запуска.
- Рабочая гипотеза: внедрение единого тестово-бенчмарочного контура для CUDA (корректность + профилирование + автотюнинг) уменьшает количество дефектов в ядрах и повышает производительность по сравнению с ручной настройкой.

**3. Научно-практические задачи**

1. Проанализировать подходы к тестированию GPU-кода и выделить практические ограничения существующих инструментов.
2. Спроектировать архитектуру библиотеки, объединяющей логику тестов, бенчмарков и управления видеопамятью.
3. Реализовать интеграцию с Google Test для автоматизации Unit-тестов CUDA-ядер.
4. Реализовать интеграцию с Google Benchmark для параметрических прогонов и изолированных измерений.
5. Реализовать метрики оценки узких мест.
6. Провести испытания на реальном проекте.

**4. Границы работы**

В рамках НИР:

- реализуется библиотека для тестирования и бенчмаркинга CUDA-ядер
- тестируется не менее 6 ядер из реального приложения
- оценивается производительность на 2 разных GPU от Nvidia

За пределами НИР:

- разработка полноценного профайлера уровня Nsight Compute
- глубокий сбор низкоуровневых данных о использовании различной памяти GPU
- тестирование CUDA-ядер в связке с CPU логикой

**5. Требования к результату**

**Функциональные:**

1. Запуск изолированных Unit-тестов CUDA-ядер с автоматической подготовкой данных и проверкой результата.
2. Автоматизированный подбор конфигурации запуска ядра по серии измерений.
3. Этапное профилирование (H2D, Kernel, D2H, Total).
4. Формирование отчетов.

**Нефункциональные**:

1. Воспроизводимость: фиксированные условия стенда, число повторов, единая методика статистики.
2. Расширяемость: возможность добавлять новые ядра и новые политики автотюнинга.
3. Практичность: простая интеграция в существующий C++/CUDA проект.
4. Наблюдаемость: прозрачные причины выбора «лучшей» конфигурации

**6. Методика исследования и критерии сравнения**

**Базовые принципы экспериментов:**

1. Для каждого сценария выполняется прогон из 30 повторов (не учитывая “разогревочные” запуски), рассчитывается 95% доверительный интервал.
2. Корректность проверяется до принятия результатов производительности.
3. Сравнение ведется на одинаковых входных данных между базовой и подобранной конфигурациями.

**Критерии оценки:**

1. Корректность работы кода.
2. Среднее/медиана времени выполнения ядра и полное время конвейера.
3. Стабильность выполнения.
4. Ускорение относительно базовой конфигурации.

- применение подхода к реальному интерактивному проекту, а не только к синтетическим примерам

Практическая полезность:

- снижение времени на рутинные проверки;
- ускорение поиска рабочей конфигурации запуска;
- раннее обнаружение узких мест по памяти и способе доступа к ней.

**8. Риски и стратегия их снижения**

1. Риск: высокая вариативность времени на загруженной системе.  
   Меры: warm-up, серия повторов, расчет CI, контроль фоновой нагрузки.
2. Риск: сильная привязка автотюнинга к конкретному GPU.  
   Меры: тестирование библиотеки будет проходить разных GPU
3. Риск: сложность интеграции с существующим движком.  
   Меры: тестирование только CUDA-части.
4. Риск: срыв сроков из-за расширения функционала.  
   Меры: поэтапный план и фиксация минимально достаточного функционального ядра.

**Часть II. Техническая (предполагаемая реализация)**

**11. Архитектура библиотеки**

Библиотека проектируется модульно:

1. core: обертки над CUDA-ресурсами, управление устройством, централизованная обработка ошибок.
2. testing: интеграция с Google Test, assert/expect-обертки для CUDA.
3. benchmark: изолированные прогоны производительности через Google Benchmark.
4. autotune: генерация кандидатов конфигурации и выбор оптимального варианта.
5. profiling: этапные таймеры на CUDA Events, сбор статистики.
6. analysis: вычисление метрик узких мест.
7. reporting: сериализация результатов для последующего анализа и вставки в записку.

**13. Алгоритм автоподбора конфигурации**

1. Определить множество кандидатов по block\_size и ограничениям устройства.
2. Рассчитать grid\_size для каждого тестового входа.
3. Для кандидата выполнить warm-up.
4. Выполнить серию измерений (30 прогонов) и собрать ProfilingBreakdown.
5. Проверить корректность результата (validator).
6. Рассчитать статистику (mean/median/p95/CI95/cv).
7. Выбрать лучший кандидат по median kernel\_ms; при равенстве использовать p95, затем cv.
8. Сформировать отчет с полным рейтингом кандидатов и причиной выбора.

**14. Подход к Unit-тестированию CUDA**

Сценарий типового теста:

1. Подготовка входных данных на хосте.
2. Выделение DeviceBuffer.
3. Копирование H2D.
4. Запуск ядра с конфигурацией.
5. Синхронизация и проверка статуса CUDA.
6. Копирование D2H.
7. Сравнение с эталоном через EXPECT\_NEAR/EXPECT\_EQ.

Пример целевого DSL-стиля:

CUDA\_EXPECT\_ARRAY\_NEAR(vectorAddKernel,

hA, hB, hOut, n,

/\*epsilon=\*/1e-5,

/\*config=\*/KernelLaunchConfig{grid, block});

**15. Профилирование и метрики узких мест**

Этапные метрики:

- t\_h2d: копирование данных на GPU;
- t\_kernel: выполнение ядра;
- t\_d2h: копирование результата на CPU;
- t\_total: суммарное время сценария.

Производные показатели:

1. transfer\_compute\_ratio = (t\_h2d + t\_d2h) / t\_kernel.
2. coalescing\_sensitivity = t\_strided / t\_linear.
3. scaling\_exponent: наклон зависимости log(t\_total) от log(N).

Интерпретация:

- высокий transfer\_compute\_ratio указывает на доминирование передачи данных;
- coalescing\_sensitivity > 1.2 указывает на чувствительность к раскладке в памяти;
- высокий cv указывает на нестабильный рантайм и необходимость доп. контроля условий.

**16. Интеграция в проект тестового движка**

Подход к интеграции:

1. Выделить CUDA-ядра в отдельный слой, доступный как из runtime движка, так и из тестов.
2. Создать адаптер запуска ядра, который принимает KernelLaunchConfig.
3. Подготовить набор фикстур с типовыми входами (малый, средний, большой объем данных).
4. Реализовать минимум 6 отдельных тестовых объектов (6 ядер).

Минимальный список тестируемых ядер:

1. Обновление плотности вокселей.
2. Интеграция физических параметров.
3. Вычисление соседства/контактных взаимодействий.
4. Фильтрация/компактификация активных элементов.
5. Генерация буферов для последующих этапов.
6. Поиск пересечений для интерактивного выбора.

**18. План тестирования и приемочные критерии**

Тестовые группы:

1. Корректность: типовые случаи, граничные размеры, float tolerance.
2. Отказоустойчивость: невалидные конфигурации, проверка сообщений об ошибках.
3. Производительность: baseline против autotune.
4. Переносимость: проверка на двух GPU.

Критерии приемки:

1. Все Unit-тесты корректности проходят.
2. Для каждого из 6+ ядер есть отчет о профилировании.
3. Для каждого ядра получена рекомендация конфигурации запуска.
4. Есть повторяемые результаты с 95% CI.
